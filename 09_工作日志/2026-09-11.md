- **【当日更正】数传改口 TELEM1 → UART4(SERIAL6)**：实物核对发现数传随附线
  **与 TELEM1 座不匹配**。改接 UART4（原 ELRS 预留口，正好空着），
  参数 `SERIAL6_PROTOCOL=2 / SERIAL6_BAUD=57 / OPTIONS=0`；TELEM1(SERIAL1)
  还原固件默认空余备用。已同步改齐：参数基线、SSOT 执行清单、02 手册
  §1/§2、03 手册 §2.3、07 技术栈、11 手册全套。接线注意：若随附插头对
  UART4 座也不匹配，剪线重做（5V/GND/TX/RX 交叉，CTS/RTS 悬空），接线前
  万用表实测。
- **【再更正 + 验收通过】数传改回 TELEM1**：找到适配 TELEM1 座的线，改回
  （SERIAL1=2/57，UART4 还原 -1 备用）。**端到端验收通过**：地面站 COM10
  收到飞控心跳流（sysid=1，15 条/15s，正好 1Hz），全链
  飞控 TELEM1 → 空中电台 → 无线 → 地面电台 → USB。
- **地面站驱动**：地面电台为 CP2102（SiLabs VCP 官方驱动已装），系统里固定

  只剩单向。换线（交叉）后秒通。

- 注意 433MHz 属于够用级链路（标称 2km 为空旷理想值），任务半径 300m 内余量充足，
  但现场存干扰时优先降空速/靠 FS_GCS_ENABLE=0 的自主兜底，不指望断链重连。

# 追加会话：RTK 调试开局——rover 上机受挫，5V/GND 反接实锤（同日晚）

> 分层隔离法：单机 USB → 接飞控 → 波特率 → 供电接线。前两层软件侧全查完，
> 断在第四层（线缆），rover 当前无供电、未损坏嫌疑待复核。

## 一、层 0：rover 单机 USB 测试（结论：Type C 无数据输出）

- Type C 直插电脑 → **CH340 枚举 COM11**（PnP 到达时间 22:19:06 确认身份；
  驱动系统自带，无需安装）。
- 8 波特率（921600/460800/230400/115200/57600/38400/9600/4800）× DTR/RTS
  拉起，**全部 0 字节** → 判定 Type C 仅供电/厂商 APP 通道，NMEA 走 6P UART
  （规格书"出厂 921600"指的是 6P 那路）。

## 二、层 2：接飞控 GPS2（飞控侧排障过程）

- `GPS2_TYPE=3(NMEA)` 写入成功；`GPS2_BAUD` 读不到 → **全参数下载 1071 个
  查明**：这版固件没有 GPS2_BAUD，GPS 口波特率跟底层串口——GPS2 映射
  SERIAL4，改 **SERIAL4_BAUD**（原值 230=230400，GPS 口固件默认）。
- `GPS_AUTO_SWITCH` 固件默认 1（自动切换）→ 按"只看不切"定案**改 0**。
- 波特率扫描 921600/115200/38400/57600 四档（每档重启+监听 GPS2_RAW）→
  **全零**。

## 三、根因：5V/GND 反接（灯不亮实锤）

- rover 灯不亮 + 所用线是"飞控自带"直通线 → 对照针序：**rover 6P
  （1=GND, 2=SCL, 3=VCC, 4=RX, 5=SDA, 6=TX）与 Pixhawk GPS 标准
  （1=VCC, 2=TX, 3=RX, 4=SCL, 5=SDA, 6=GND）完全相反**，1 对 1 直通 =
  5V 进 GND 脚，模块无供电。
- 损伤评估：Type C 期间 CH340 曾正常枚举 → 模块大概率存活；正确供电后复核。

- **飞行冒烟 FLIGHT_OK（修正后）**：起飞精确悬停 8.01 m → 降落 → 落地检测 →
  上锁。修复前的"验证通过"其实带着两个潜伏 bug（见 §二）。
- **全任务 M1 闭环 DONE**（新脚本 `fc_sitl_mission.sh`）：WAIT_FCU → WAIT_NAV_STABLE

## 二、fly.py 三修（都是"旧验证掩盖下的潜伏 bug"）

1. **直连 + 数据流请求**：裸 SITL（reset_sim 栈）无 MAVProxy，旧 `udpin:14550`
   永远等不到心跳 → 支持 `python3 fly.py tcp:127.0.0.1:5760`。实测裸 SITL **只发
   心跳**、其余消息零流 → 加 REQUEST_DATA_STREAM ALL @10Hz（SR0_* 被固件静默
   忽略的又一实证，与本日凌晨 dryrun 结论互证）。
2. **起飞高度 bug（09-10 的"30 s 爬升 55.8 m"同源）**：Copter 把 NAV_TAKEOFF
   param7 按 **ABOVE-HOME** 解释，旧代码传"AMSL+8"，而 SITL 家点海拔 584 m →
   实际目标 ~592 m；30 s 观察窗 + `max_rel>5` 宽松判据把 51.6 m 的持续爬升掩盖成
   "验证通过"。修后直接传 8.0，实测稳悬 8.01 m。
3. **落地判定提前放弃**：`recv_match` 一次迭代只吃一条消息，40 次循环在 10 Hz 流
   下 ~5 s 就耗尽，下降未完即误报 landed=False → 改 90 s **时间窗**轮询；
   FLIGHT_OK 判据加 `max_rel<20 且 landed`；只在确认落地后才发 disarm。

## 三、坑与教训（全部实测，操作侧入册 13 手册 §6）

| 坑 | 结论 |
|---|---|
| `gz sim -g` 首挂 EGL 初始化失败退场 | 直接重跑一次即好；窗口判据 `xwininfo -root -tree \| grep 'Gazebo Sim'` |
| 跨机 GUI 不可行 | Jetson Harmonic(8) vs Windows Jetty(10)，gz transport 跨大版本不互通；远程看画面走 VNC，Mission Planner 可 TCP 5760 看 HUD（与 MAVROS 错峰） |
| `pgrep/pkill -f` 自匹配 | 本命令行含同样字符串会误杀自己/误计数（本次实证：ssh 255 + gui=1 假阳性）；用 `[x]ode` 写法、`-x` 或窗口探测代替 |
| reset_sim.sh 的 `nohup gz sim` 未接 `</dev/null` | 后台进程持有 SSH 会话 stdin → ssh 不退（进程本身无害，setsid/nohup 已保命）；待修一行 |
| 5760 端口竞争 | MAVROS（状态机/干跑）与 fly.py 都走 tcp 5760，勿并行 |
| WAIT_GUIDED 是设计关口 | 状态机不自己切 GUIDED（= 飞手确认语义），`auto_arm_on_guided` 只管之后的解锁；全自主仿真需外部 `set_mode GUIDED` 扳机（比赛时由遥控器切，语义不变） |
