## 二、坑清单新增/澄清（全部实测）

1. **ardu.log 的 "Waiting for connection" 是假信号**：源码定位
   `AP_HAL_SITL/UARTDriver.cpp:424`——只是 SERIAL0 的 TCP 5760 在等客户端，
   **与 Gazebo 握手毫无关系**。reset_sim 末尾 tail 长期显示这行 ≠ 卡死。
2. **ardu.log 块缓冲**：stdout 重定向到文件后是块缓冲，tail 看到的是几分钟前的
   历史，"卡在启动"多为假象。已在启动行加 `stdbuf -oL` 行缓冲。
3. **SERIAL0(5760) 单客户端 + reset_sim 原来不杀 mavros**：泄漏的 mavros 自动
   重连抢槽 → 下一次任务的 mavros TCP 连得上但拿不到流 → 永远 `mode:''`
   （本次现象的直接放大器）。5762(SERIAL1)/5763(SERIAL2) 是同一 FCU 的第二/三
   出口——探活/旁听走 5762，不挤 5760。
4. **ros2 topic echo --once 探 /mavros/state 假阴性再实证**（09-10 老坑）：
   00:34 成功轮的 40s 探测照样 WARN，实际 mavros 早已连上。链路判据一律
   pymavlink 直探，不碰 DDS。

   自己杀了。老规矩再次验证：kill 与 start 拆两条、写成脚本文件执行、`[x]` 括号

## 二、动力整定（09-09 定案规格落地：整机 ~8kg、单桨 28~31N）

- **方法**：取 gz-sim LiftDrag 源码精推 T = 2·cl·½ρ·(cp·ω)²·area（叶片入流恒沿
  forward ⇒ α≡a0=0.3，cl=cla·a0=1.275，双叶纯竖直出力；CW 转子 forward 镜像、
  对称成立），再用原 iris 已知悬停 cmd≈0.53 交叉验证公式无误，最后从"单桨
  29.5 N"反解参数——全程无拍脑袋。
- **参数表**（两份 model.sdf）：

  | 参数 | 原 (Iris) | 新 | 依据 |
  |---|---|---|---|
  | 整机质量 | 1.75 kg | 8.00 kg（base 7.75） | 09-09 "~8 kg 级" |
  | 惯量 base | 0.008/0.015/0.017 | 0.061/0.114/0.129 | 质量×轴距比例放大 |
  | 惯量 桨 | 9.75e-6/1.667e-4 | 1.735e-5/2.97e-4 | 随桨径² ×1.78 |
  | LiftDrag area/cp | 0.002 / ±0.084 | 0.00356 / ±0.112 | 桨径 1.334 倍缩放 |
  | multiplier | ±838 | ±656（6264 rpm） | 满油门单桨 29.5 N，T/W=1.50 |
  | cmd_max | ±2.5 | ±4.0 | 满转速阻力矩 2.65 N·m，原值会饱和 |

- **cmd_max 饱和是隐形坑**：P 控制 + 关节阻尼的稳态力矩超过 cmd_max 时静默转不到
  目标转速（转速差 -4% → 推力差 -8%），必须先算阻力矩再定上限。
- 前节 §五 的"拉力倍率待办"由此**清账**：656 即 29.5 N 标定值（6.856e-5·ω²），

# 追加会话（三）：任务仿真"横着搜"修复——出生朝向与场地方向差 90° + 场地几何对齐

> 现象：Jetson 跑 `fc_sitl_mission.sh`，SEARCH 段飞机没有朝场地（投放区）方向飞，

## 一、根因（证据链）

1. 世界文件出生位姿 `iris_d435i` 为 `<pose ... 0 0 90>`（yaw=90°，机头朝世界
   +Y/北）；而场地沿世界 **+X** 延伸（RULE_MAPPING.md：投放区中心 (30,0)、
   侦察区 (55,0)，scene.yaml/generate_scene.py 同）。
2. mission_node 的任务坐标系约定 = "场地 x 轴锁定在起飞瞬间机头方向"
   （`lock_frame()`：mission_yaw ← compass_hdg，`field_to_local()` 旋转）。
   于是场地系 x=机头(+Y)，预设搜索航线（field x 6→10）整体转 90° 飞向 +Y——
   桶阵（+X≈28m）全程在航线侧面，看起来就是"没向前飞、横着搜"。
3. 09-11 日志自证：LOCK_FRAME 打印"航向 0.0°"= 机头朝北 = yaw90 出生，
   与场地 +X 差 90°，完全吻合。
4. 排除机模找补：make_zd550_meshes.py 只做 mm→m 缩放 + z 平移，无旋转，
   yaw=90° 非网格补偿，属上游示例遗留。

# 追加会话（五）：数传"MP 无法配置"定案——口选错 + X-Rock 固件 AT 门控被心跳流锁死（同日晚）

## 一、现象与排查实录

- **现象**：MP → 初始设置 → 可选硬件 → SiK电台(数传) → 加载设置，**页面全空全灰**
  （版本/RSSI/波特率/Net ID 一概读不出）；截图时右上角连的是 **COM5**。
- **链路本身健康（先排除链路嫌疑）**：pyserial 直连 COM10——
  ① 1Hz MAVLink 心跳持续在流（seq 递增）= 飞控→TELEM1→机载台→433→地面台→PC 下行通；
  ② MP 选 COM10@57600 连接后参数进度条正常前进 = 上行（PC→…→飞控）同样通。
  **数传链路双向都好，零硬件问题。**
- **COM 口身份核对**：COM5 = ArduPilot MAVLink（飞控 USB），COM6 = SLCAN，COM10 = CP2102（地面电台）。
- **AT 命令模式探测**（决定性实验）：裸 `+++` 全波特率（9600~230400）共 12+ 次全败；
  `+++\r` 在 2.0s 静默窗口下 **1 次成功**，`ATI` 应答 **"X-Rock 4.0"** → 远航 X6 不是
  标准 SiK 固件！随后 9 次重试又全败，且失败与否与静默长度强相关。

## 二、根因（两坑叠加）

1. **口选错**：SiK 电台配置页是对"电台"发 AT 指令的，用户选了 COM5（飞控 USB）——
   AT 指令全发给了飞控，页面必然全空。配置页必须选 **COM10** 且**不点"连接"**。
2. **X-Rock 固件的 AT 门控 × 1Hz 心跳流**：进命令模式要求 `+++` 前后各 ~1s 串口静默，
   链路上心跳每 0.97s 一帧，"后静默"窗口必被打断——**带活链路配置电台几乎不可能**
   （实测 25 次成 1 次，成功那次大概率是心跳恰好迟到）。标准 SiK 同样受此约束，
   官方/CUAV 教程"单独给电台上电配置"正是这个原因。

## 三、处置与固化

- **新脚本** `03_工具/飞控调试/check_radio.py`：链路活性（MAVLink 帧计数）+ AT 双序列
  轮试 + ATI 系列转储（只读不改参，自动给"先断机载端"建议）；工具 README 同步；
- **手册更新**：03_操作模块 §3.3 重写为"日常零配置 + 静默配置四步法"（断机载端电 →
  COM10+57600+不点连接 → 加载设置 → 不行用脚本核身/3DR Radio Config），§3.5 排障表
  新增"SiK 电台页全空"行；06_坑清单 §10 新增同款坑行；
- **当前电台不需要任何改动**：出厂配对完好、链路验收通过；唯一未来需求 = 赛场撞频改
  Net ID，届时按静默流程操作即可。

## 四、教训（归入家规"判别式探针"）

"无法配置"不等于"链路坏了"——先用 pyserial 看端口上有没有数据流，再分层：
链路活性 → 口的身份 → 配置协议本身。本次三步各 10 分钟，直接把"玄学"钉成两条根因。

## 五、验证闭环（追加）

- 机载端断电后重跑 `check_radio.py`：`+++\r` **第 1 次尝试即进入** AT 模式，
  `ATI`→"X-Rock 4.0"、ATI2→78、ATI3→43（ATI5 无响应，X-Rock 不支持该转储变体）。
  **"心跳流锁死 AT 门控"由推断升级为实锤**；ATO 已退出，COM10 已释放。
- 用户随后在 MP 点"加载设置"弹 `InvalidOperationException: 端口被关闭`——堆栈
  `Sikradio.BUT_getcurrent_Click → RFD900.TSession.PutIntoATCommandMode →
  DetermineMode → IsInBootloaderXMode → SerialPort.Write`。定性：MP 1.3.83 电台页
  走的是 RFD900 会话代码，进命令模式失败后走备用探测路径撞上已关闭端口，
  抛出丑陋异常对话框——**与全空同源（AT 进不去）的另一种表现**，非新硬件故障。
  静默窗口内重试是正解；MP 若仍弹窗，用 3DR Radio Config 或脚本核身。

## 一、真判读节点（M4 侦察判读的真实现）

- 实现：`cuadc_perception/hazard_recon_node.py`（+ `config/hazard_recon_params.yaml`
  + `launch/hazard_recon.launch.py` + setup.py 注册）。链路 = Image → engine 帧级
  检测（全分辨率像素坐标）→ FrameGate 门控（灰区 ROI 放大重推，每帧上限 4 次防
  级联）→ MarkerFusion 窗口融合 → `/cuadc/recon/classification`（Reliable 10）。
  握手语义复用 fake_recon_node：capture_done = 证据窗口已开启，判定异步不阻塞任务。
- det 模型 runner-up 口径（契约 v1.2 注记）：top1 = 框置信度；runner-up = 同位置
  （IoU≥0.45）**异类**竞争框最高置信度——det 每框单类，类别竞争 = 同位置异类框对峙。
- 工程五件套：engine SHA-256 强校验（params 钉死 964cd588…，不符拒启）；黑帧预热
  3 帧（journal 留痕）；每帧心跳 `/perception/heartbeat_recon`（含空帧，fail-closed）；
  证据落盘 1s/张 JPEG + 结论 JSONL（tmp+rename 原子写），磁盘 <512MB 停证告警。
- **联测结果**（测试驱动注 val 拼图 10Hz + capture_request seq=7）：握手→窗口→
  判读全链通，**99 帧投票确认"有毒品 conf0.86"**，JSONL+裁剪图+窗口 JPEG 齐全。
  驱动端 12s 超时没等到属测试脚本时序（判读按契约异步发布，节点日志/证据为准）。

## 二、当晚大坑（实测定案，均已修复入库）

1. **runner-up O(n²) 张量陷阱**：帧打点定位"单帧 2.6s"→ detect 占 2.61s——52 框
   两两配对循环里直接索引 torch 张量（逐元素 GPU 算术+逐次同步）；一次性
   `.cpu().numpy()` 转纯 float 后 detect 2.6s→**39ms**，整帧 65ms@52 框。
2. **SHM 共享内存被仿真栈搅乱**：同机 gz/arducopter（同为 DDS 参与者）运行时，
   节点进程活着但**不在节点图上**（端点零匹配、话题零到达）。`fastrtps_udp_only.xml`
   （UDPv4-only）后恢复——本会话并发仿真线（会话五/六）的栈还开着时发生的，
   profile 已固化进 systemd 启动链。
3. **UDP 分片丢帧**：UDP-only 后大图 best_effort 订阅丢一个分片=丢整帧（10Hz 只吃
   ~2.5Hz）；图像订阅改 **RELIABLE**（depth 2）靠重传保整帧。正解 = 调大内核
   `net.core.rmem_max`（需 sudo，比赛机待办）。
4. **老坑两连发新变体**（06_坑清单已更新）：①ssh 命令行"脚本内括号写法+同命令行
   明文关键字"照样 pkill 自杀——含 kill 的操作单独一条 ssh 且整条命令行不得出现
   明文关键字；②`&&` 长链被 `&` 整体后台化（含 source），前台裸跑找不到 rclpy——
   多步远程操作写成脚本文件执行。
