# 01 · 视觉模块（相机 → 数据 → 训练 → 部署 → 感知输出）

## 怎样使用本文

- **视觉算法队友**：按 §2→§3→§4 把数据→训练→部署跑通，§5 契约是写感知节点前的必读，§1.2 是拍数据/上机前必须设置的；
- **联调队友**：只看 §5（契约）与 §7（视觉在环）；
- **材料边界**：训练/检测的**算法原理**（为什么这么设计）在 [04_算法模块](04_算法模块.md)；源码在 `10_机载代码/cuadc_perception/`，本文摘关键段讲解。方案权威：SSOT §4/§8。

## 先记住三个区别

1. **训练在云端，推理在机上**——Jetson 上不训练（太慢），AutoDL 租 4090 训完导 engine；
2. **val 分数 ≠ 比赛成绩**——线上 val 是代理指标，比赛验收以**现场实拍验证集**为准（必须独立保留）；
3. **颜色是类别特征**——所有涉及颜色空间增强/灰度的决定都围绕这一条。

## 0. 模块全景

视觉系统在整机里的位置：**下视相机取流 → YOLO 推理（TensorRT）→ 后处理 → 单目解算 → 按契约发布筒位/判读结果**，供状态机消费（状态机见 04 算法模块 §6）。

要训/要部署的模型三件：

| 模型 | 架构 | 数据 | 用途 | 状态 |
|---|---|---|---|---|
| 危化标识分类 | YOLOv8n-det | 合成 2220 张 + 实拍 414 张 | 侦察判读 10 类 | 🔶 流水线就绪待跑（P0.1） |
| 白筒检测 | YOLOv8n-seg | v1 barrel 2200 框 + 白筒实拍（缺口） | 投放目标检测 | ⬜ 待实拍数据 |
| H 圆检测 | YOLOv8n 单类 | 自制 ø80cm ~200 张（缺口） | 精准降落 | ⬜ 待采集 |

模块验收门汇总（全部达标 = M2"能看"过关）：

| # | 验收项 | 标准 |
|---|---|---|
| 1 | 训练精度 | 逐类 mAP50 ≥0.90（逐类无豁免）、漏检 <5% |
| 2 | 机载推理 | 稳态 ≥25FPS（占位权重实测 52.8，双倍余量）；首帧（含黑帧预热）<10s |
| 3 | 实拍检出 | 白筒检出 ≥95%（独立现场验证集） |
| 4 | 拒识策略 | 低置信自动留空生效（τ=0.7 / margin=0.3） |
| 5 | 契约校验 | `check_vision_contract.py` 全项 PASS（不过不许上机） |

## 1. 相机硬件与成像基线

### 1.1 相机规格（BL-500W-335 板机）

| 项 | 规格 |
|---|---|
| 传感器 | 1/2.8"，2.0μm 像元，2592×1944 最高 |
| 镜头 | 2.8mm 定焦，D105° / H81.8° / V66° |
| 输出 | UVC（USB2.0），MJPG / YUY2 |
| 关键帧率 | 1080p@30 (MJPG)、640×480@30 (YUY2) |
| 曝光控制 | 自动曝光/自动白平衡可关；亮度/增益/曝光等 12 项可调 |
| 供电/功耗 | 5V，≤160mA |
| 尺寸/重量 | 38×38mm 板 / 157.4g（含支架 304.9g） |

用途：下视安装（检筒 + H 圆 + 俯拍标识）。仿真里对应 iris_d435i 的下视 RGB-D（`/d435i/*` 四路话题）。

### 1.2 曝光基线（实飞定案，勿用自动曝光）

- **快门 ≤1/500s**：定量依据——6m/s 飞行速度下，1/250s 运动模糊 6.4px，直接吃掉小目标；
- **手动锁曝光**：参考冠军队实飞值 `exposure 120 / gain 64 / 50Hz 工频抗闪`；
- **禁自动曝光**：场地灯光变化时自动曝光会瞬间"失明"，检测全丢；
- 上机操作：v4l2 查帧率/锁定曝光参数（相机上机前的必修项）；
- 帧率 ≠ 快门速度：30FPS 的相机，每帧曝光仍可能 1/60s——**先锁快门再谈帧率**。

> ⚠️ **09-13 上机实测：本台 BL-500W-335 的手动曝光不受控**——标准 UVC
> `exposure_time_absolute` 写入被接受但固件无视（20~2047 全程亮度不变），无厂商
> 扩展单元可绕。自动曝光正常但暗光下拉秒级长曝光会把帧率拖到 ~1fps。**上机红线
> "锁快门 ≤1/500s" 当前无法执行**，飞行前必须解决（换固件工具路径/换相机，或
> 实证户外日光下 AE 短曝光足够稳后再豁免）。bench 现行方案：手动模式（固件固定
> 短曝光）+ `brightness=48` 补亮 + 开灯拍摄。另：v4l2 控制必须在开流**前**写
> （流中写入掉 ~1fps 怪模式），相机节点 `10_机载代码/scripts/camera_node.py`
> 已固化此顺序。详见 06 坑清单 §5。

### 1.3 对准平面与高度来源（成像相关定案）

- 高度只用飞控相对高度（TFmini 4m 以下辅助），**不用气压**（2~5m 桨风 ±0.5m 跳变）；
- 瞄准的是**桶口平面**：`alignment_z = 目标参考高 − 0.30m`（筒高 0.30m，冠军队标定工具里的坑）。

### 2.3 数据集构建复现（`build_real_data.py`）

```bash
cd 02_数据与训练 && python build_real_data.py
```

**脚本内部逻辑**（三条固化纪律 + 实现）：

1. **剔除无关截图**：按"哈希命名 + PNG 格式 + 无标注"三特征识别（本批混入 31 张电调接线图截图）；
2. **按视频片段切分 train/val**——这是防"验证泄题"的关键：
   - `frame_*` 连续帧系列（234 张）→ 取**中段连续帧**做 val，其余 train；
   - `1_*` 系列（79 张）→ 取**末段**做 val；
   - `0000_frame_*` 单帧片段（101 张）→ 每帧本就独立，随机 10% 进 val；
   - **连续帧绝不跨集**：同一视频里相邻帧几乎一样，随机切分 = val 里全是 train 见过的画面 = 分数虚高上场翻车；
3. **无标注实拍帧补空标签文件**（YOLO 训练自动当背景图，教模型"这里没目标"）；
4. `data.yaml` **不写 `path` 键**（以 yaml 所在目录为根，换机器免改路径）：

```yaml
# real_data/data.yaml（附件 11 十类 + barrel；⚠️ train/ 现存标签是旧表类别号，
# 重映射前此 yaml 仅为格式示例——见 §2.2 资产表与 build_real_data.py 头部警告）
names:
  0: 爆炸品
  1: 不燃气体
  # ……（附件 11 十类，顺序与 §2.1 表一致）
  10: barrel
train: images/train
val: images/val
```

校验口径：414 图 ↔ 414 标签一一对应，无缺无孤儿；逐类分布 train 201~241 / val 9~32。SRC/DST 跟随脚本目录（`Path(__file__).parent`），整个目录挪走也能跑。

### 2.4 数据集版本管理

- 命名链：`hazard_synth_v1` → `hazard_mix_v2` → `hazard_mix_v3…`；数据快照与权重同名存档；交付包自动带 `dataset_version.md` + data.yaml 快照；
- **现场实拍验证集必须独立保留**（模拟比赛当天筒和光照），不并入训练集——比赛验收以现场集为准，线上 val 只是代理指标。

### 2.5 采集计划（贯穿全程的缺口关闭）

1. 白筒三种规格（15/20/25cm）真实地面（蓝底/水泥地）实拍，**含斜视角**；
2. H 圆 ø80cm 自制 ~200 张；
3. 标识实拍**优先补 刺激性/放射性物品**（v2 未达标两类，蓝地场景）+ 蓝地背景负样本（v2 混淆矩阵背景误报集中于此），再补至每类 ≥300（当前 ~240/类）；
4. 每批新数据走 §2.3 切分逻辑 + 现行直训路线（SSOT §8.2），迭代 v3。

拍摄基线照 §1.2（快门 ≤1/500s、手动曝光）。

### 3.2 参数铁律（写死在 `run_v2_training.sh`，勿改）

| 参数 | 值 | 原因 |
|---|---|---|
| 起点 | v1 best.pt 微调 | 不从头训（合成集已学到的特征是底子） |
| `epochs` | 150 | — |
| `lr0` | **0.001** | 微调学习率必须比从头训降 10 倍，否则把 v1 权重冲毁 |
| `flipud` | 0.5 | 俯视图上下翻转 = 白赚的增强（无人机视角无"上下"语义） |
| `hsv_h` | **0.005** | **色相就是类别特征**（红=易燃、橙=爆炸品）；默认 0.015 会把红色增强成橙色 = 主动制造标签噪声 |
| `close_mosaic` | 10 | 最后 10 轮关 mosaic，贴合真实分布（mosaic 拼图训练收敛快但分布偏） |

v1 基线（合成集）：yolov8n、100ep、mAP50≥0.97。

### 3.3 验收判读速查

| 线 | 标准 |
|---|---|
| 逐类 mAP50 | **≥0.90（逐类无豁免**；deliver_v2 的 val_report 即按此判读） |
| 漏检率 | <5%（召回 ≥0.95） |

排障速查：

- 单类偏低 → 先看混淆矩阵和谁混（火焰三件套/白底系互混是重灾区），再确认该类 val 实例数（每类仅 9~32 个，偶发波动正常，别急着下结论）；
- 小目标漏检普遍偏高 → 试 `imgsz=1280` 重训（改脚本第 5 步），**先和部署端对齐推理尺寸**（改了训练尺寸必须同步改导出/推理尺寸）；
- 单类 mAP50=0 断崖 → 八成标签类别号错位，抽查几张图的 txt 与实际贴纸对照；
- OOM → `batch=8`；推倒重来 → `rm -rf runs real_data`。

### 4.3 部署铁律

- **engine 与"权重 + 设备"双绑定**：本机导出一次 9min46s——**换权重必须重建 engine；比赛日绝不可现场构建**；
- **黑帧预热**：TensorRT 首帧有秒级初始化（CUDA context + kernel 加载）。启动流程固定跑 3 张 CUDA 假图再上岗——吃"上场 1 分钟"规则的红利：赛前 suspend，唤醒即跑；
- **`numpy<2` 铁律**：Jetson 上 pip 装 anything 都要守住（装 onnx 曾把 numpy 升到 2.2.6，系统 cv2 numpy1 ABI 直接炸 `numpy.core.multiarray failed to import`，降回 1.26.4 才恢复）；
- **pip 必须走清华镜像**：Jetson 直连 pypi 会卡死在依赖解析（9-12 首跑 `pip install` 干等 3 分钟+ 无输出）——`deploy_trt_jetson.sh` 已内置 `-i 清华源`，手动装包照做；
- 上场口径（SSOT §9.1）：预加载模型 → 黑帧自检 → suspend → 上场唤醒到首帧 <10s。systemd 自启见 §4.4（已上线）。

### 4.4 systemd 自启（P0.3，09-12 上线）

- 文件：`10_机载代码/systemd/cuadc-perception.service` + `cuadc_start_perception.sh` + `fastrtps_udp_only.xml`；
- 安装（一次）：单元文件 → `/etc/systemd/system/`，脚本 → `~/cuadc_start_perception.sh`，profile → `~/cuadc_udp_profile.xml`，然后 `sudo systemctl enable --now cuadc-perception`；
- 行为：开机自动加载 engine + 3 帧黑帧预热后待命（journal 实测启动→就绪 8s）；engine 缺失/SHA 不符拒启，systemd 按 Restart=on-failure 每 10s 重试（fail-closed，不许带错权重上岗）；
- 查看：`journalctl -u cuadc-perception -f`（"引擎就绪"行有加载/预热耗时）；
- **UDP-only profile 必须带**：同机跑仿真栈（gz/arducopter 也是 DDS 参与者）时 SHM 共享内存段会被搅乱导致节点图不可见（09-12 实测），UDP-only 后恢复；
- 真判读节点 `hazard_recon_node` 同机联调实测：Image→门控→窗口融合→判读发布+握手+证据 JSONL 全链通（99 帧确认判例）；帧处理 ~65ms@52 框。**大坑存档**：runner-up 竞争度 O(n²) 循环里直接索引 torch 张量 = 秒级（52 框 2.6s），一次性转 numpy 后 <5ms。

### 4.5 图像传输定案（09-13 上机实测：压缩透传是唯一可用路）

| 传输方式 | 实测 | 结论 |
|---|---|---|
| raw `Image`（1080p BGR，6MB/帧） | 单帧序列化/发送 ~1s，全链 **1Hz**；RELIABLE 下慢订阅端还会把发布端流控堵死 | **不可用**（09-12 的 UDP 丢帧问题之上又叠了序列化开销） |
| JPEG 重编码 `CompressedImage`（95 质量） | ~17Hz（重编码吃 ~20ms/帧） | 可用但没必要 |
| **相机原生 MJPEG 直透**（`CONVERT_RGB=0`，~65KB/帧） | **30fps 全链稳定**，零编码零二次压缩（色彩保真利于判读） | ✅ **定案**：`camera_node.py` 默认此模式 |

配套三件（缺一不可）：

1. 发布端 QoS **best_effort**（RELIABLE 会被慢订阅端拖死）；订阅端必须 `image_qos_reliable: false` 匹配——**RELIABLE 订阅 + BEST_EFFORT 发布 = QoS 不兼容，一帧都收不到**；
2. 判读节点订阅 `<image_topic>/compressed`（参数 `image_compressed: true`，09-13 新增）；
3. 相机驱动 `10_机载代码/scripts/camera_node.py`：v4l2 控制（曝光模式/亮度）必须在**开流前**写（流中写掉 ~1fps 怪模式），每次 `open()` 后自动重设（设备重开会丢控制值）。

### 5.1 检测话题 `/perception/drop_buckets_body`

`geometry_msgs/PoseArray`，每个 Pose = 一个白筒候选，**机体系（frame_id=`cuadc_body_flu`）**：

| 字段 | 复用含义 | 说明 |
|---|---|---|
| `position.x/y/z` | 筒口中心机体系坐标（米） | x 前 y 左 z 上，z 通常为负（筒在飞机下方） |
| `orientation.x` | **筒口直径估计**（米） | 感知端反算，状态机用来对号 15/20/25cm |
| `orientation.y` | **置信度** [0,1] | 后处理四件之后的质量分 |
| `orientation.z` | **契约版本哨兵**（当前 1.0） | 所有 pose 必须一致；不一致 = 违约，接收方整帧拒用 |
| `orientation.w` | 保留 | 固定 0.0 |
| `header.stamp` | **取帧时刻** | 不是发布时刻！（§5.3） |

硬性要求：频率 ≥25Hz；**空帧也必须发**（0 pose 的 PoseArray = "这帧没看到"）；单帧 ≤8 个；同帧去重（中心距 <2cm 合并）在感知端完成；QoS best_effort（SensorDataQoS，丢帧优于堵塞）。

### 5.2 发布端标准写法（摘自 `fake_perception_node.py`，真感知必须复用此语义）

```python
def on_timer(self):
    # 关键契约：stamp = 取帧时刻（这里 = now − 注入延迟），不是发布时刻
    capture_time = self.get_clock().now() - Duration(seconds=self.delay_s)

    msg = PoseArray()
    msg.header.stamp = capture_time.to_msg()
    msg.header.frame_id = self.frame_id          # 'cuadc_body_flu' 哨兵
    for x, y, z, d, c in zip(self.bx, self.by, self.bz, self.bd, self.bc):
        pose = Pose()
        pose.position.x = x + random.gauss(0.0, self.noise)
        ...
        pose.orientation.x = d      # 复用：筒口直径（m）
        pose.orientation.y = c      # 复用：置信度 [0,1]
        pose.orientation.z = self.version  # 复用：契约版本哨兵
        msg.poses.append(pose)
    self.bucket_pub.publish(msg)

    # 心跳与检测同源同节奏，空帧也发（fail-closed：停发 = 故障）
    hb = Header()
    hb.stamp = capture_time.to_msg()
    hb.frame_id = 'fake_perception'
    self.heartbeat_pub.publish(hb)
```

三个要点：① stamp 减去 pipeline_delay 模拟"取帧在先"；② orientation 字段复用带哨兵；③ **心跳与检测同节奏发布**——消费方靠心跳新鲜度判故障，停发 = 故障 = 禁投（fail-closed），不需要显式"故障消息"。

### 5.3 时间戳约定（P0.4）

1. `header.stamp` = **图像取帧时刻**（相机驱动回调瞬间），推理/排队/发布耗时不算；
2. 管线延迟上界 1.5s、未来戳容差 0.05s、odom 包围两帧最大间隔 0.2s（违反即丢帧，绝不外推）；
3. 所有节点读写 stamp 前换本节点时钟类型（`use_sim_time` 下 rclcpp::Time 相减抛异常的隐形坑，已写死消费端代码）。
原理与量级论证见 04 算法模块 §4。

### 5.5 侦察判读消息定义（全文，`cuadc_interfaces/msg/`）

```text
# ReconClassification.msg —— 侦察判读融合输出（AI 判读；不在飞控关键路径上，组员据此填单）
std_msgs/Header header           # stamp = 融合窗口末帧的取帧时刻（不是发布时刻）
uint32 viewpoint_seq             # 对应 /cuadc/recon/capture_request 的 point.x 序号
ReconMarker[] markers            # 本窗口结论，可空数组 = 本窗口无任何结论

# ReconMarker.msg —— 单个物理标识的判读结论（语义见 接口契约.md §5）
# class_id 取值 = 附件11 的 10 类（0..9，与训练集 data.yaml 顺序一致）
uint32 marker_index      # 本架次内稳定序号（按首次出现顺序，0 起）
int32 class_id           # 0..9；-1 = 拒识留空（留空 0 分，错填 -100，宁空勿错）
float32 confidence       # 融合窗口内该类置信度中位数 [0,1]
float32 margin           # top1-top2 中位数（类别竞争度）
uint32 frames            # 支持该结论的帧数
bool ambiguous           # true = 两类票数竞争被拒识（地面站须醒目提示转人眼备份）
string evidence_path     # 证据目录（机载相对路径，可为空串）
```

QoS：Reliable(10)——低频结构化结果一条不许丢（与检测流 best_effort 相反）。

#### ④ 摆靶（摆得好坏直接决定有没有结论）

| 摆法要点 | 原因 |
|---|---|
| **开灯**，标识朝上、正对相机 | 暗屋 AE 拉长曝光掉帧率（§1.2 警示框）；倾斜贴纸 = 桌面验证也失真 |
| 标识距镜头 **0.5~1.5m**（举高相机或镜头朝下放地上） | 模型 imgsz=640，标识在画面里占 **1/10~1/4** 边长最稳；贴脸或太远都掉检出 |

| 一个窗口只摆**一个**标识 | 融合按标记关联，多个也能出但读结果费劲 |
| 摆好后**保持静止**到窗口结束 | 融合要 ≥5 帧同意 + 置信中位数 ≥0.8，窗口 4s 内晃动会稀释 |

#### ⑤ 发侦察请求（seq 必须递增，重复的会被忽略）

```bash
source /opt/ros/humble/setup.bash
export FASTRTPS_DEFAULT_PROFILES_FILE=$HOME/cuadc_udp_profile.xml
timeout 4 ros2 topic pub -r 1 /cuadc/recon/capture_request \
  geometry_msgs/msg/PointStamped "{point: {x: 3.0}}"   # 下次改 x: 4.0、5.0 …
```

- `point.x` = viewpoint_seq，**每个节点记住发过的 seq，重发同号直接忽略**——上面
  `-r 1` 跑 4 秒会发 4 次，只有第一次生效，其余刷"收到重复 … 忽略"属正常，别用
  `-r` 常驻循环发布（会一直撞号刷屏）；
- **不要用 `--once`**：同机多订阅者时它只等到第一个匹配上的订阅者就发，其余节点
  收不到（09-13 实测：生产收到了、bench 没收到）；短循环让 DDS 有时间送达全员；
- 发布器也要带 **UDP-only profile**：生产服务是 UDP-only 参与者，裸发布器（默认
  SHM+UDP）与它匹配不稳，可能丢请求；
- 窗口 4s 后自动收口出结论，不用再发任何东西。

## 7. 视觉在环仿真（sim-to-real 零改码）

- 仿真里用 iris_d435i 的下视 RGB-D：话题 `/d435i/image`、`/d435i/depth_image`、`/d435i/points`、`/d435i/camera_info`（本机 Windows 与 Jetson 均实测出流）；

- 场地随机布设：`generate_scene.py` 按 seed 撒桶/标识，真值落 `config/generated_scene.yaml`（固定 seed 回归对比用）。
