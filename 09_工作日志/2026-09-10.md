# 追加会话：bat 启动器排障——GZ_SIM_RESOURCE_PATH 尾部分号毁掉模型加载（同日晚）

> 用户反馈双击 `launch-cuadc-sim.bat` 后 GUI 只剩框架：实体树空、仿真时间 N/A、
> Entity 0；起初疑似那条 Qt QML 相对 URL 警告，实为无辜。

## 定位过程（对比法逐层收窄）

- **判别加载成败的快速探针**：`gz topic -l | grep d435i`——正常加载有 12+ 传感器/
  位姿话题；失败实例只有 clock/stats/state 少数世界话题，模型全部缺席
- 进程与服务都在（gz-sim-main + gz-sim-gui-client，world 服务照常广播）→ 断在
  环境变量环节。杀残废实例重跑 bat 复现：仍无 d435i（期间还见到 /world/shapes——
  gz sim 收不到有效 world 时会静默回退默认示例世界，也是判别线索）
- 等价复现排除法：`cmd /c "set GZ_SIM_RESOURCE_PATH=<路径>&& pixi run gz sim -s -r"`
  无头跑 → 模型正常（12 话题）→ **cmd 设变量本身没问题**
- 诊断版 bat 把 `%~dp0`/`%WORLD%` 展开值落日志 → 展开全对 → 唯一差异锁定：
  bat 里 `set "...models;%GZ_SIM_RESOURCE_PATH%"` 在变量未定义时尾部留了**空分号**

## 根因（A/B 实锤）

完全相同的启动命令，仅资源路径一个带尾部分号一个不带：

- `...models;`（尾分号）→ **0 个模型话题，世界空**
- `...models`（无尾分号）→ 12 个模型话题，全要素加载

本 gz 构建（conda-forge gz-sim 10 Jetty）解析 `GZ_SIM_RESOURCE_PATH` 时，路径列表
出现空尾项会把整个解析搞坏。此前 `gz topic -e`/`gz service --req` 全废的
DynamicFactory proto 问题属于同一打包质量的另一处，互不相关。

## 修复与端到端验证

- `launch-cuadc-sim.bat` 改为条件追加：`if defined GZ_SIM_RESOURCE_PATH (...追加)
  else (...单路径)`，并在 bat 内留注释警告
- 双击等价方式启动验证：12 模型话题齐 + 无 shapes 回退 + GUI 截图确认实体树
  （cuadc_field / takeoff_pad / drop_1~3 / recon_1~5 / hazard_* / iris）与场地
  渲染全部正常 ✅
- 复用的诊断产物已清理（debug bat、测试日志）

## 二、踩坑清单（全部实证，逐个排掉）

1. **~/ardupilot 源码是 CRLF**（当年从 Windows 传上去）：waf-light 的 shebang 变成
   `python3\r` → exec 127。修法 `sed -i '1s/\r$//' waf-light`（.py 文件本身吃 CRLF
   无所谓，只有直接 exec 的文件的 shebang 致命）
2. `python` 命令不存在（22.04 默认）→ `apt install python-is-python3`
3. sim_vehicle 报 mavproxy.py 不存在：**非登录 shell 的 PATH 无 ~/.local/bin** →
   start_sitl.sh 显式 export PATH。副作用：sim_vehicle 会 "Killing tasks"（它的
   mavproxy 起不来就杀全家），但 arducopter 可能成孤儿存活，排障时注意甄别
4. **pkill 自匹配又中两回**（09-09 §九的坑变异）：启动命令文本里含待杀的关键字时，
   kill 与 start 必须拆成两条 ssh；`[x]` 技巧只防"模式串自身"，防不了"同串后文"
5. **场地模型无碰撞体**：纯物理 world 里无人机从起飞坪直接穿地自由落体（高度掉到
   -275 km），起飞指令被拒的真正根源。修法：飞行 world 内联一块 400×200 m 静态
   碰撞地面（jetson/cuadc_rescue_flight.sdf，已去掉 Sensors 渲染系统，不占 GPU；
   IMU 走 gz-sim-imu-system 不受影响）
6. **eeprom 里 FRAME_CLASS=0 / FRAME_TYPE=1**（重建二进制后旧参数区失效）→
   "Arm: Motors: Check frame class and type"。fly.py 启动自检并修复为 1/0；
   注意改 frame 后需重启飞控重建电机矩阵；`-w` 每次抹回坏默认值，已从启动脚本移除
7. SITL 的 SERIAL0(TCP 5760) 单客户端：MAVProxy 连上后第二个客户端（脚本）收不到
   心跳。统一走 MAVProxy 的 UDP 14550 出口
8. takeoff 返回 UNSUPPORTED(4) 的两个来源：① 不在 GUIDED（STABILIZE 直接拒）
   ② EKF 高度已疯（坠机污染）。诊断脚本务必先设模式、按 command id 过滤 ACK
9. 旧 SITL 实例会记住坠机状态的 EKF 污染——换 world 修好地面后 SITL 也要重启
10. ssh 会话挂住：setsid 分离的子进程继承 stderr fd → 本地 ssh 等关闭。放后台
    任务时注意主动 TaskStop，改用新连接查询状态

# 追加会话：MAVROS + cuadc_mission 状态机对接 SITL（同日深夜，干跑推进到 WAIT_GUIDED ✅）

> 目标：任务状态机吃上 SITL。结果：状态机 WAIT_FCU → WAIT_NAV_STABLE → LOCK_FRAME
> （坐标系锁定 home=(0,0,0.18) 航向 0°）→ PRESTREAM → WAIT_GUIDED，全链路推进正常。

## 一、链路架构（定案）

```
arducopter SITL（裸跑，无 sim_vehicle/MAVProxy）
 ├─ ArduPilotPlugin ←→ Gazebo（JSON 9002/9003）
 └─ SERIAL0 = TCP 5760 ←— mavros fcu_url="tcp://127.0.0.1:5760" ←— cuadc_mission
```

- **MAVROS2 不认 udpin:// URL**（Unknown URL type），直接用 `tcp://127.0.0.1:5760`
- **MAVProxy 层全部砍掉**：它只当转发器还挑链接状态，裸跑 SITL 反而稳定
  （start_sitl.sh / reset_sim.sh 直接跑 arducopter 二进制 + --defaults 参数链）

## 二、本次踩坑（个个实证）

1. **SITL 控制台读 stdin**：ssh 会话一关 stdin 到 EOF，arducopter 静默退出（无
   segfault、无 oom、journal 无痕）——"飞几分钟就死"的真凶。修法 = sim_vehicle 同款
   `sleep infinity |` 保管道（reset_sim.sh 已内置 setsid + stdin keeper）
2. **4.7-beta 无 SR0_* 参数**（又一处参数迁移）：mavros 不主动要流 ArduPilot 就不发，
   LOCAL_POSITION_NED/odoom 完全没数据。SR0 文件被静默忽略，正确姿势 =
   MAVROS `set_message_interval` 服务逐条订阅（干跑脚本 [3.5] 段已固化：SYS_STATUS/
   ATTITUDE/LOCAL_POSITION_NED/GLOBAL_POSITION_INT/VFR_HUD/BATTERY_STATUS/
   EXTENDED_SYS_STATE @10Hz），执行后 odom 出流 4.7 Hz，状态机立刻过导航门禁
3. `ros2 topic echo --once` 探 connection 不可信（DDS 发现慢，09-09 坑复发）——
   状态机节点日志才是真连接判据（它的 WAIT_FCU→WAIT_NAV_STABLE 迁移 = mavros 真通）
4. 我自己的两个低级坑复用记档：① sed 跨字替换吃掉空格（sim_vehicle.py-v）；
   ② ssh 远程命令里 kill 与 start 同串导致 pkill 自杀——kill/启动必须分两条，
   或写成脚本文件执行
5. 调试期间大量"幽灵死亡"其实是我自己排队的后台任务互相重置抢端口——**严格串行
   单线程操作**后才收敛
